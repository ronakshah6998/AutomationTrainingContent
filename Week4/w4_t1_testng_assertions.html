TestNG Assertions & Verification State

Establish automated testing checkpoints, validate complex UI and API systems, and manage hard vs. soft test lifecycles.

🔴 Hard Assertions 🟡 Soft Assertions 🕹️ Interactive Sim 🧠 MCQ Check
What are Assertions?

Assertions are verification checkpoints in your test script that confirm whether the application's actual behavior matches the expected outcome.

💡
Why Assertions? Without assertions, a Selenium script that navigates through a page and triggers no internal Java exceptions will always be reported as PASSED — even if the page loads completely empty or displays a critical error screen. Selenium interacts; TestNG Assertions decide success or failure.
🚀

Verification

Evaluating whether a specific component acts as intended (e.g. does clicking 'checkout' lead to payment?). Assertions check logic.

📋

Validation

Determining whether the high-level business workflow fulfills requirements (e.g. does the system allow a guest user to buy items?).

🧠

Assertion Lifecycle

Step-by-step evaluation where mismatches throw an AssertionError, causing the framework to fail the running test method instantly.

Selenium Alone is Not Enough

Selenium is exclusively an automation tool, not a testing tool. Learn the distinction below:

1

Actions vs Checkpoints

Selenium can write text into fields using sendKeys() and click buttons using click(). It cannot evaluate whether the resultant greeting text is grammatically correct or if the landing dashboard values are accurate.

2

Framework Governance

TestNG reads the resulting AssertionError stacktraces. This enables custom execution control, parallel thread execution, test reporting, and Jenkins build pipelines to read the exit statuses.

Types of Assertions: Hard vs Soft

TestNG structures verification into two categories based on their termination policies.

Feature Hard Assertion Soft Assertion
Class Name org.testng.Assert org.testng.asserts.SoftAssert
Failure Impact Terminates test execution instantly Collects failure, continues executing test steps
Throw Exception At the line of failure Only at the end when calling .assertAll()
Usage Scenario Blocking checkpoints (Login fails, DB down) Independent checks (Cart list, field styling)
Real-World Validation Contexts

Choosing between Hard and Soft assertions is a critical skill for design reliability.

🔴 Hard Assert Contexts

Login Verification: If login fails, subsequent steps (searching, checkout) cannot run. Stopping early saves server overhead.

🟢 Soft Assert Contexts

Dashboard Fields: Verify account balance, username, recent statements, and interest rate simultaneously. Check all before failing.

Hard Assertions (The Assert Class)

Methods inside org.testng.Assert operate statically. If an assertion condition evaluates to false, an AssertionError is thrown immediately, bypassing all remaining lines of code in that specific test method.

⚠
Immediate Termination: Once a Hard Assertion fails, the test method is marked as FAILED, and the execution jump-exits. Any cleanup steps inside the method are skipped. Best Practice: Always perform cleanup inside @AfterMethod hooks to ensure they run regardless of test failures.

Enterprise Hard Assertion Script
☕ LoginHardTest.java
package com.enterprise.tests;
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.testng.Assert;
import org.testng.annotations.Test;
public class LoginHardTest {
code
Code
@Test
public void verifyUserLoginFlow() {
    WebDriver driver = new ChromeDriver();
    driver.get("https://bank.com/login");

    // Step 1: Submit Credentials
    driver.findElement(By.id("username")).sendKeys("admin");
    driver.findElement(By.id("password")).sendKeys("secret");
    driver.findElement(By.id("loginBtn")).click();

    // Step 2: Validate current landing URL
    String actualUrl = driver.getCurrentUrl();
    String expectedUrl = "https://bank.com/dashboard";
    
    // Parameters: Assert.assertEquals(actual, expected, customMessageOnFailure)
    Assert.assertEquals(actualUrl, expectedUrl, "Landing Page URL mismatch after login redirection!");

    // Step 3: Check Welcome Message displays (Only run if URL matches!)
    boolean greetingStatus = driver.findElement(By.id("welcome")).isDisplayed();
    Assert.assertTrue(greetingStatus, "The user welcome dashboard message is absent!");

    driver.quit();
}
}
Syntax and Parameter Deep-Dive

Notice the parameter order: TestNG asserts actual first, then expected. This is the reverse of JUnit.

1

assertEquals(actual, expected, message)

Compiles string representation comparison. If it fails, reports "Landing Page URL mismatch after login redirection! expected [https://bank.com/dashboard] but found [https://bank.com/login]".

2

assertTrue(condition, message)

Validates a boolean statement. In this test, it ensures greetingStatus is true. If false, it drops a clean AssertionError with your custom descriptive message.

Soft Assertions (The SoftAssert Class)

Sometimes, you want to perform multiple validations on a page (e.g. checking several elements on a profile page) without stopping the entire test at the first failed check. This is where SoftAssert is used.

🔑
How it works: Soft Assertions are not static. You must instantiate a new object: SoftAssert soft = new SoftAssert();. If a soft assertion fails, it logs the failure but allows execution to continue. To report all compiled failures and fail the test, you must call soft.assertAll(); at the very end.
Soft Assertion Lifecycle Flow
🚀
Step 1
Navigate to Profile Page
↓
🟡
Step 2
soft.assertEquals(profileEmail, expected) -> FAILS (logged, continues)
↓
🧪
Step 3
soft.assertTrue(avatar.isDisplayed()) -> PASS
↓
⚡
Step 4
soft.assertAll() -> Checks compiled history
↓
💥
Result
Test fails now, reporting Step 2 as the failure reason.
🚨
The Silent Danger: If you forget to invoke soft.assertAll(); at the end of your test method, the test will pass even if every single assertion inside it failed. Always ensure assertAll() is the absolute last line of execution.
Complete Soft Assertion Example
☕ ProfileSoftTest.java
package com.enterprise.tests;
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.testng.annotations.Test;
import org.testng.asserts.SoftAssert;
public class ProfileSoftTest {
code
Code
@Test
public void verifyUserProfileDetails() {
    WebDriver driver = new ChromeDriver();
    driver.get("https://bank.com/profile");

    // 1. Instantiate the SoftAssert object locally
    SoftAssert soft = new SoftAssert();

    // 2. Validate Profile Email
    String actualEmail = driver.findElement(By.id("email")).getText();
    soft.assertEquals(actualEmail, "user@bank.com", "Profile Email mismatch!");

    // 3. Validate Account Holder Name (Continues running even if email verification fails!)
    String actualName = driver.findElement(By.id("holder")).getText();
    soft.assertEquals(actualName, "John Doe", "Holder Name mismatch!");

    // 4. Validate Premium Member Status
    boolean isPremium = driver.findElement(By.id("premium")).isSelected();
    soft.assertTrue(isPremium, "User is not marked as premium!");

    driver.quit();

    // 5. Compile and throw any exceptions gathered
    soft.assertAll();
}
}

Real World E-Commerce Checkout Validation

This enterprise-level test validation ensures the entire cart total math remains correct after a customer checks out.

☕ CartValidationTest.java
package com.ecommerce.checkout;
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.testng.asserts.SoftAssert;
import org.testng.annotations.Test;
public class CartValidationTest {
code
Code
@Test
public void validateCartSummaryInvoiceMath() {
    WebDriver driver = new ChromeDriver();
    driver.get("https://ecommerce-shop.com/checkout");

    SoftAssert soft = new SoftAssert();

    // Fetch details
    String priceText = driver.findElement(By.id("subtotal")).getText(); // "$100.00"
    String taxText = driver.findElement(By.id("tax")).getText();         // "$8.00"
    String totalText = driver.findElement(By.id("grandtotal")).getText(); // "$108.00"

    // Execute asserts: soft validations ensures mismatches on subtotal doesn't prevent grandtotal analysis
    soft.assertEquals(priceText, "$100.00", "Base Subtotal price verification failed!");
    soft.assertEquals(taxText, "$8.00", "Calculated tax mismatch!");
    soft.assertEquals(totalText, "$108.00", "Invoice grand total summary mismatch!");

    driver.quit();
    soft.assertAll();
}
}
💡

Line-By-Line Breakdown

Each string output from selectors is soft-asserted. Even if subtotal displays incorrectly, the test continues to check the computed tax, compiling a comprehensive failure log.

🎤

Interview Tip

If an interviewer asks: How do you assert that parallel execution runs safely with SoftAssert? Explain that you must instantiate it locally inside each test method to prevent cross-thread contamination.

Common Assertion Pitfalls

Review common errors in automation design that lead to fragile suites and misleading test results.

🔴 Error: Forgotten assertAll() inside SoftAssert tests

What happened?

By executing soft validations without invoking assertAll(), the test class processes errors internally but never notifies TestNG. The test method returns a false success state, hiding critical product defects.

❌ Incorrect (Passes Silently)
SoftAssert soft = new SoftAssert();
soft.assertEquals(actualText, expectedText);
// Missing soft.assertAll()!
✅ Correct
SoftAssert soft = new SoftAssert();
soft.assertEquals(actualText, expectedText);
soft.assertAll();
🔴 Error: Declaring SoftAssert as a Static Class-Level Variable

What happened?

Declaring a single static SoftAssert instance causes tests executing in parallel threads to write to the same assertion history. This leads to leaked failure states across completely unrelated test executions.

❌ Incorrect (Leakage Hazard)
public class ProfileTest {
static SoftAssert soft = new SoftAssert();
// Sharing state across parallel runs!
}
✅ Correct (Thread-Safe)
@Test
public void testProfile() {
SoftAssert soft = new SoftAssert();
// local instance per thread
}
🔴 Error: Swapping expected and actual arguments

What happened?

TestNG uses the parameter structure assertEquals(actual, expected). Confusing this with JUnit's structure assertEquals(expected, actual) will produce confusing reports when assertions fail, reversing the expected and actual values.

❌ Incorrect (JUnit Order)
Assert.assertEquals("Dashboard", driver.getTitle());
// Reports: expected [actualTitle] but found [Dashboard]
✅ Correct (TestNG Order)
Assert.assertEquals(driver.getTitle(), "Dashboard");
// Reports: expected [Dashboard] but found [actualTitle]
