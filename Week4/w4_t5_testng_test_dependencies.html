Test Dependencies & Execution Control

Establish strict execution prerequisites, handle skip propagation automatically, and ensure robust cleaning operations with TestNG [2].

🔗 dependsOnMethods 📁 dependsOnGroups ▶ Live Playground 🔄 alwaysRun=true
What are Test Dependencies?

A test dependency is an execution constraint instructing TestNG that a specific test method must run only after one or more other test methods have successfully completed [2].

💡
The Enterprise Problem: In standard testing environments, TestNG runs tests alphabetically or pseudo-randomly by default [2]. This works for isolated unit tests, but enterprise automated regression suites validate multi-step business transactions [2]. Attempting to execute a payment test when the setup login test has failed results in a broken environment, orphaned browser processes, and false-positive reporting [2]. Setting explicit test dependencies structures these runs [2].

Core Transaction Business Workflow Example [2]

login() ➔ searchProduct() ➔ addToCart() ➔ checkout() ➔ payment() ➔ logout()

Why Checkout cannot execute before Login: WebDriver scripts operate within context [2]. The checkout page is secured behind an authenticated session cookie [2]. Attempting to navigate directly to the checkout page without first establishing session cookies in the login step causes a redirect to the home screen [2]. Running tests out of order fails the checkout verification and exposes the system to unnecessary setup steps [2].

Selenium Best Practices: When to Depend

Understand the design boundaries between independent unit tests and dependent integration tests [2].

Scenario Context Independent Tests (No dependencies) Dependent Tests (Explicit dependencies)
Core Philosophy Every test is self-contained. Sets up and tears down its own state [2]. Tests inherit the current system state from previous executions [2].
Primary Application Rest APIs, independent utilities, core forms, search checks [2]. Complex transactional flows (checkout pipelines, bank transfers) [2].
Failure Behavior Only the failing test is highlighted. All other tests run [2]. Failing a parent test automatically skips all downstream dependent tests [2].
Speed Impact Can run in parallel across any distributed thread pools [2]. Must run sequentially within the dependency thread constraint [2].
💡
Interview Tip: If an interviewer asks, "Should UI automated tests be independent?" the best answer is: "Ideally, yes. Independent tests are parallel-friendly and isolated [2]. However, for multi-step End-to-End business flows (like booking a flight, completing payment, and verifying confirmation), using dependencies prevents false positives and saves resources by skipping downstream tests if a prerequisite step fails [2]."
TestNG Dependency Mechanisms

TestNG provides three main properties within the @Test annotation to control test dependencies [2].

1. dependsOnMethods Attribute

Specifies that the annotated test method depends on the successful completion of other methods [2].

☕ Java: dependsOnMethods Usage
@Test
public void login() {
// Sets up cookie session context
}
@Test(dependsOnMethods = {"login"})
public void searchProduct() {
// Runs only if login() completed successfully
}
What happens to downstream tests under dependsOnMethods:
  • Parent Passes: The dependent test runs normally [2].
  • Parent Fails: TestNG skips the dependent test immediately, marking it as SKIPPED in report metrics [2].
  • Parent is Skipped: The dependent test is also skipped [2]. This creates a skip propagation cascade down the dependency chain [2].
2. dependsOnGroups Attribute

Specifies that the annotated test depends on the successful completion of an entire group of tests [2].

☕ Java: dependsOnGroups Usage
@Test(groups = {"security"})
public void oauthChallenge() { }
@Test(groups = {"security"})
public void credentialEncryption() { }
@Test(dependsOnGroups = {"security"})
public void paymentGatewayCheck() {
// Executes only after ALL tests marked in "security" group pass successfully
}
3. alwaysRun = true Attribute Override

Forces the execution of a dependent test even if its parent tests fail or are skipped [2].

☕ Java: alwaysRun = true Usage
@Test(dependsOnMethods = {"paymentGatewayCheck"}, alwaysRun = true)
public void terminateSessionCleanup() {
// Runs even if paymentGatewayCheck() fails or is skipped [2]
// Prevents memory leaks and orphaned browser driver sessions [2]
}
Comparison Matrices

dependsOnMethods vs. dependsOnGroups

Property dependsOnMethods dependsOnGroups
Scope Tightly coupled to specific, single method name strings [2]. Decoupled and tied to logical group patterns [2].
Flexibility Low. Renaming a parent method requires updating all dependent tests [2]. High. New tests can be added to the target group without altering dependents [2].

Dependency vs. Priority

Property dependsOnMethods priority = N
Execution Guarantee Guarantees that a parent test must run and pass before dependents start [2]. Only hints at the execution order. Does not guarantee prerequisites are met [2].
Failure Resiliency If a parent test fails, dependents are safely skipped [2]. If a low-priority test fails, high-priority tests run anyway, causing cascading false failures [2].

alwaysRun=false vs. alwaysRun=true

Property alwaysRun = false (Default) alwaysRun = true
Parent Failure Behavior The dependent test is automatically skipped [2]. The dependent test runs anyway [2].
Primary Application Functional validations that require prerequisite data [2]. Cleanup operations, database connection closings, and browser teardowns [2].

 Common Errors & Fixes


These test configuration mistakes are common when managing TestNG suite dependency chains [2].













🔴 TestNGException: Circular dependency detected in the suite execution graph




What happened?


Class method A depends on method B, and method B depends on method A [2]. This creates a circular loop [2]. TestNG fails to resolve the execution path and throws a TestNGException before running any tests [2].


org.testng.TestNGException:
Cyclic dependency found: [PaymentTest.processPayment() depends on PaymentTest.validateSession(), PaymentTest.validateSession() depends on PaymentTest.processPayment()]




❌ Wrong (Circular loop)
@Test(dependsOnMethods = {"processPayment"})
public void validateSession() { }
@Test(dependsOnMethods = {"validateSession"})
public void processPayment() { }


✅ Correct (Linear order)
@Test
public void validateSession() { }
@Test(dependsOnMethods = {"validateSession"})
public void processPayment() { }




✅ Fix: Avoid circular references [2]. Keep your dependency trees linear and flowing in one direction [2].


💡 Interview Tip: If asked, "What happens if TestNG detects a circular dependency?" explain that TestNG won't run any tests [2]. It aborts execution and throws a TestNGException during the early suite compilation phase [2].









🔴 TestNGException: Method 'loogin' not found in dependsOnMethods list




What happened?


TestNG resolves dependsOnMethods keys as exact, case-sensitive strings [2]. If there is a typo in a method name string, TestNG throws a TestNGException at startup because it can't find the target method [2].


org.testng.TestNGException:
com.training.tests.CartTest.search() depends on nonexistent method com.training.tests.CartTest.loogin()




❌ Wrong (Typo in string)
@Test
public void login() { }
@Test(dependsOnMethods = {"loogin"})
public void search() { }


✅ Correct (Exact match)
@Test
public void login() { }
@Test(dependsOnMethods = {"login"})
public void search() { }




✅ Fix: Always double-check your method names in dependsOnMethods strings [2]. Use your IDE's refactoring tools to rename methods safely without breaking string references [2].









🔴 TestNGException: Dependent method is not enabled




What happened?


If you set enabled = false on a test method, TestNG ignores it during compilation [2]. However, if another test method depends on it, TestNG throws an exception because the prerequisite test cannot execute [2].


org.testng.TestNGException:
com.training.tests.PurchaseTest.checkout() depends on method com.training.tests.PurchaseTest.login(), which is not enabled.




❌ Wrong (Depends on disabled test)
@Test(enabled = false)
public void login() { }
@Test(dependsOnMethods = {"login"})
public void checkout() { }


✅ Correct (Both enabled)
@Test
public void login() { }
@Test(dependsOnMethods = {"login"})
public void checkout() { }




✅ Fix: Never depend on a disabled test method [2]. If you must disable a parent test, make sure to temporarily disable all of its dependent tests as well [2].









🔴 Logic Defect: Functional assertions run even after prerequisite setups fail




What happened?


Using alwaysRun = true on a functional validation test (like checkout) is an anti-pattern [2]. If the prerequisite setup test (login) fails, the system state is broken [2]. Running the checkout test anyway causes unnecessary failures and pollutes reports [2].




❌ Wrong (alwaysRun on functional test)
@Test(dependsOnMethods = {"login"}, alwaysRun = true)
public void checkout() {
// Runs even if login() fails, causing false-positive errors [2]
}


✅ Correct (alwaysRun only for teardown)
@Test(dependsOnMethods = {"login"})
public void checkout() {
// Skips safely if login() fails [2]
}
@Test(dependsOnMethods = {"checkout"}, alwaysRun = true)
public void teardown() {
// Cleanups should use alwaysRun=true [2]
}




✅ Fix: Only use alwaysRun = true for cleanup or teardown methods [2]. Let functional validations skip naturally if their prerequisites fail [2].
